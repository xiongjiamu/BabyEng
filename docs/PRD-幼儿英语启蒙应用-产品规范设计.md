## 1. 产品概述

### 1.1 产品定位

面向 1~3 岁幼儿及其母亲的双角色英语启蒙工具。母亲英语水平有限，需要「边学边教」；幼儿以视听与跟读为主。应用部署在个人服务器上，通过移动端浏览器（PWA）使用，不依赖应用商店审核。

核心价值用一句话讲清：**母亲用中文说一句「这是什么」「妈妈用英语怎么说」，应用即时返回中文、英文、音标和英语发音，母亲跟着学一遍再教孩子，孩子跟读并录音回放对比。**

### 1.2 目标用户画像

应用存在两个强耦合的用户角色，任何功能设计都必须同时回答「母亲怎么用」和「孩子怎么用」。

**主用户：母亲（操作者 + 辅助学习者）**

| 维度 | 描述 |
|---|---|
| 英语水平 | 基础有限，能读简单单词但发音不自信，音标不熟 |
| 使用动机 | 想在家给幼儿做英语启蒙，但不信任自己发音、不知教什么 |
| 设备能力 | 熟练使用手机，会用语音输入（中文） |
| 痛点 | 怕教错发音；不知道按什么顺序教；难以坚持 |
| 期望 | 门槛低、即时反馈、能学能教、有进度感 |

**终端用户：1~3 岁幼儿（学习者）**

| 维度 | 描述 |
|---|---|
| 认知特征 | 注意力短（单次专注 1~3 分钟），以视听和模仿为主，不识字 |
| 语言能力 | 处于母语爆发期，可同步建立第二语言语音印象 |
| 操作能力 | 能点触大图标、能跟读，但不能阅读文字、不能复杂操作 |
| 风险点 | 屏幕时间需控制；发音不准是常态，不能严格打分 |

**双角色使用模型**：母亲发起 → 应用呈现 → 母亲示范 → 幼儿跟读 → 应用录音 → 母亲与幼儿共同回放对比。整个流程母亲始终在场，应用不是「带娃工具」而是「亲子教学脚手架」。

**年龄分段**：1~3 岁跨度内幼儿能力差异极大，12 月龄和 35 月龄几乎是两个物种，不能用同一套交互。后续所有幼儿侧设计按下表两段区分。

| 分段 | 月龄 | 幼儿能力 | 交互方式 | 屏幕策略 |
|---|---|---|---|---|
| A 段 | 12~24 月 | 不能稳定完成持续按压，不能做选择题，注意力 1~2 分钟 | 幼儿不操作应用，全部由母亲代操作；幼儿只听、只看、只跟读 | 默认纯音频模式（见 6.6），屏幕主要给母亲看 |
| B 段 | 24~36 月 | 能点触大目标，能做二选一，注意力 3~5 分钟 | 幼儿可点大按钮，可做听音选图 | 允许看图，单次 5 分钟 |

分段由 `child_birthdate` 自动推导，母亲可在设置里手动覆盖。文档中凡写「幼儿点击 / 幼儿录音」之处，A 段一律理解为母亲代操作。

### 1.3 核心使用场景

| 场景 | 触发 | 母亲动作 | 应用响应 | 幼儿参与 |
|---|---|---|---|---|
| 物品教学 | 指着杯子 | 语音问「杯子英语怎么说」 | 返回 cup /kʌp/ + 发音 | 跟读、录音 |
| 人物教学 | 看到爷爷 | 语音问「爷爷」 | 返回 grandpa /ˈɡrænpɑː/ + 发音 | 跟读、录音 |
| 数字教学 | 吃水果时 | 语音问「三个」 | 返回 three /θriː/ + 发音 | 跟读、数数 |
| 情绪教学 | 孩子开心 | 语音问「开心」 | 返回 happy /ˈhæpi/ + 发音 | 跟读、做表情 |
| 短句教学 | 日常场景 | 语音问「该睡觉了」 | 返回 Time for bed + 发音 + 场景例句 | 跟读整句 |

### 1.4 设计目标与原则

**四条设计原则，优先级从高到低**：

1. **母亲可教性优先**：所有功能首先回答「母亲能不能立刻用起来教」，而非「功能炫不炫」。发音必须准、音标必须显示、中文释义必须直白。
2. **幼儿低门槛**：界面大图标、大字号、强对比色；操作以「点一下」「跟读」为主，不要求阅读；单次会话控制在 5 分钟内。
3. **即时反馈**：库内词问答 1.2 秒内出结果，界面 800ms 内必须有可见变化，TTS 即点即播，录音即录即放（分路径预算见 4.1.3）。延迟会直接击穿母亲的使用耐心。
4. **节制与安全**：屏幕时间提醒、护眼提示、无诱导消费、无外部链接、数据本地化。

### 1.5 非目标（Non-goals）

明确不做什么和明确做什么同等重要，写在这里避免后续需求反复。

本产品不做识字、拼写与字母教学，1~3 岁的目标是语音印象而非文字符号。不做英语以外的第二语言，多语种会稀释词库校音与发音质量上的投入。不做社交、家长社区、排行榜以及任何跨用户可见的数据。不做订阅、内购、广告与任何形式的商业转化。不做无人陪伴的自动连播式内容，母亲在场是产品成立的前提而不是可选项。不做真人出镜视频课程，持续产出成本个人项目撑不住（理由见 12.3）。不追求用户规模，本产品服务单一家庭，多家庭能力只是部署形态上的顺带结果，不为它做产品妥协。

## 3. 教学场景与内容体系

### 3.1 场景一：日常物品

覆盖家具、餐具、衣物、食物、玩具、家电六小类，每小类 8~12 词，首期共约 60 词。

| 小类 | 示例词条 | 难度 |
|---|---|---|
| 家具 | chair, table, bed, sofa, door | 易 |
| 餐具 | cup, bowl, spoon, fork, plate | 易 |
| 衣物 | hat, shoe, sock, coat, dress | 易 |
| 食物 | apple, milk, bread, egg, banana | 易 |
| 玩具 | ball, car, doll, block | 易 |
| 家电 | light, fan, phone | 中 |

### 3.2 场景二：人物与人物关系

| 关系层 | 词条 | 备注 |
|---|---|---|
| 直系 | mom, dad, baby | 高频 |
| 长辈 | grandpa, grandma | 高频 |
| 同辈 | brother, sister | 视家庭 |
| 自身 | boy, girl, me, you | 代词入门 |
| 称呼 | uncle, aunt | 视家庭 |

### 3.3 场景三：基础数字

1~10 必学，11~20 选学。数字需配套可数名词例句，如「two apples」「five fingers」。

### 3.4 场景四：简单情绪表达

| 情绪 | 词条 | 配套表情 |
|---|---|---|
| 开心 | happy | 😊 |
| 难过 | sad | 😢 |
| 生气 | angry | 😠 |
| 害怕 | scared | 😨 |
| 困 | sleepy | 🥱 |
| 饿 | hungry | 🍚 |
| 饱 | full | 😌 |

情绪词条配套表情贴纸，便于幼儿建立「词—表情」关联。

### 3.5 场景五：日常简短句子

按生活时段编排，每时段 3~5 句，首期共约 25 句。

| 时段 | 示例句 | 用途 |
|---|---|---|
| 起床 | Good morning. / Wake up. | 唤醒场景 |
| 吃饭 | Time to eat. / Yummy! | 用餐 |
| 玩耍 | Let's play. / Be careful. | 互动 |
| 睡前 | Time for bed. / Good night. | 入睡 |
| 出门 | Let's go. / Hold my hand. | 安全 |

### 3.6 内容分级与难度递进

全部内容分三级，母亲可在设置里切换或让应用按进度自动推进。

| 级别 | 范围 | 目标 |
|---|---|---|
| L1 入门 | 物品 + 人物 + 数字 1~5 | 建立语音印象，能跟读 |
| L2 进阶 | 情绪 + 数字 6~10 + 物品扩展 | 能主动指认 |
| L3 综合 | 短句 + 场景组合 | 能在情境中使用 |

### 3.7 内容生产与素材来源

内容量清点：首期物品约 60 词、人物 13 词、数字 10 词、情绪 7 词、短句 25 句，合计约 115 条。这批内容的生产是 MVP 里最容易被低估的工作量——写代码之外，它是唯一一件无法自动化跳过的事。

每条词条的完整交付物包括中文主词与别名列表、英文、经校验的音标、配图、经试听的 TTS 音频、例句、母亲学习卡要点七项。按人工 3~5 分钟一条估算，115 条约需 6~10 小时；若后续扩到 500 词则是 25~40 小时。可行路径是 LLM 批量生成初稿后人工逐条校验，但**音标与 TTS 音频两项必须 100% 人工过耳**，这是整个产品可信度的底线：母亲之所以用它，就是因为不信任自己的发音。

| 交付物 | 生产方式 | 校验要求 |
|---|---|---|
| 中文别名列表 | LLM 生成候选 + 人工补口语说法 | 至少覆盖 3 种日常说法（如 杯子/水杯/喝水杯） |
| 音标 | 词典查询为主（见 4.1.2） | 词典未收录的逐条人工确认 |
| 配图 | **优先自家实物照片**，其次 CC0 图库 | 单主体、背景干净、非抽象插画 |
| TTS 音频 | 预生成缓存 | 逐条试听，语速、重音、连读不可接受则换音色重生成 |
| 例句 / 母亲学习卡 | LLM 生成 + 人工删改 | 不出现语法术语，只给可直接照说的句子 |

配图优先用自家实物照片，不只是为了规避版权。1~3 岁幼儿对自家那只杯子的识别度和情感连接，远强于图库里陌生的杯子，这一步顺带把「认图」变成「认物」。母亲拍照上传应做成产品内的一个轻功能（拍照 → 自动裁方图 → 绑定词条），而不是靠手工塞文件。

词库的持续扩充不靠拍脑袋补词，而由真实未命中查询驱动：母亲问过但库里没有的词全部落表（见 8.8），按出现频次排序进入待补清单。这是本产品词库增长的主要来源。

## 4. 核心功能详细设计

### 4.1 语音问答教学（M1，核心入口）

**功能描述**：母亲用中文语音提问，应用识别后从词条库匹配或由 LLM 生成，返回中文词、英文词、音标、英语 TTS 发音，必要时附场景例句。

**输入与输出契约**：

| 输入 | 输出字段 | 备注 |
|---|---|---|
| 中文语音「杯子」 | 中文：杯子；英文：cup；音标：/kʌp/；发音：TTS 音频 | L1 别名命中 |
| 中文语音「三个苹果」 | 中文：三个苹果；英文：three apples；音标：/θriː ˈæplz/；发音：TTS；例句：I have three apples. | 数字 + 名词组合走 L4，英文与例句由 LLM 生成，音标逐词查词典拼接（见 4.1.2） |
| 中文语音「该睡觉了」 | 中文：该睡觉了；英文：Time for bed；音标：/taɪm fɔːr bed/；发音：TTS；场景：睡前 | 句子库命中 |
| 中文语音「妈妈的口红」 | 相近词推荐 + 文字输入入口 | 库外且 LLM 未启用，静默写入未命中表（8.8） |
| 未识别 | 「没听清，再说一次」+ 文字输入兜底 | ASR 置信度低 |
| 识别歧义 | 「你是说 杯子 还是 被子？」二选一 | L2 模糊层相似度接近阈值 |

**处理流程**：

1. 母亲按住录音键说话（母亲侧用按住式，幼儿侧的录音交互不同，见 4.3）。
2. 前端采集音频上传后端。
3. ASR 中文识别，返回文本。
4. 文本进入匹配管线（见 4.1.1）：归一 → 别名精确 → 模糊 → 向量近邻 → LLM 兜底。
5. 命中层级决定数据来源：库内词条直接取；走到 LLM 时输出结构化 JSON（见数据结构 Word/Sentence），但音标不采信 LLM 输出，另按 4.1.2 取。
6. 后端取 TTS 音频：缓存命中直接返回文件，未命中则实时合成。
7. 前端展示卡片 + 播放按钮并自动播放一次。注意本次会话的第一次播放必须由用户手势触发以解锁音频上下文（iOS 限制，见 9.2），此后可自动播放。

#### 4.1.1 输入归一与匹配管线

「词条库精确匹配」是本设计里最容易被高估的一环。母亲的真实说法千变万化，同一只杯子会被说成「杯子」「水杯」「这个杯子」「喝水的那个」「妈妈杯子英语怎么说」，ASR 输出还会带语气词和同音错字，字符串精确比对的命中率会远低于预期，而 9.6 里「词条库覆盖 90% 高频场景」这个假设正是建立在它之上。因此匹配必须是分层管线而非单点比对。

| 层 | 处理 | 命中后行为 | 预期耗时 |
|---|---|---|---|
| L0 归一 | 去标点与语气词、剥离「英语怎么说」等提问框架、去指示代词与量词、繁简与数字统一 | 产出归一 query，交给下层 | < 5ms |
| L1 别名精确 | 查 `word.zh` 与 `word.aliases`（同义词、口语说法、常见方言叫法） | 直接返回词条 | < 5ms |
| L2 模糊匹配 | 编辑距离 + 拼音相似度，处理 ASR 同音错字（被子/杯子、事故/柿子） | 高于阈值直接返回；接近阈值时给母亲二选一确认 | < 20ms |
| L3 向量近邻 | 中文句向量检索词库，处理描述式提问（V1 引入，MVP 不做） | Top1 距离达标则返回，否则下沉 | < 100ms |
| L4 LLM 兜底 | 结构化生成中英释义与例句，音标另取 | 返回结果并写入「待入库候选」 | 秒级 |

彻底未命中时不能只回一句「没听清」。必须同时做三件事：推荐同类目的相近高频词让母亲有台阶下，提供文字输入重试，把这条 query 写入未命中表（见 8.8）。第三件最重要——它把一次失败的交互变成了词库增长的输入。

#### 4.1.2 音标来源（不得由 LLM 直接生成）

音标是母亲最信任、也最容易被误导的字段，而 LLM 生成音标错得隐蔽：格式合法、看着像那么回事，音节和重音却是错的。母亲照着念错一遍，孩子就记错一次，这比不给音标更糟。音标按以下顺序取，任何一步都不允许直接采信 LLM 输出。

先查内置发音词典（CMUdict 派生的 ARPAbet→IPA 映射即可覆盖绝大多数英语常用词），词典未收录时用 g2p 工具生成（espeak-ng 的 IPA 输出适合做这件事——它做 TTS 音质不合格，但字素到音素转换是成熟方案），两步都失败则该词条标记为「音标待确认」，前端隐藏音标字段只给发音和释义，不给一个可能错的音标。词库内所有词条的音标在入库前人工过一遍（见 3.7）。

#### 4.1.3 性能预算与降级

原「端到端 2 秒」是一个笼统目标，既不能指导实现也无法验收，按路径拆分如下。测量口径统一为局域网、中端安卓机、P95。

| 路径 | 目标 | 预算拆解 |
|---|---|---|
| 库内命中（L0~L2） | ≤ 1.2s | 上传 200ms + 转码 100ms + ASR 500ms + 匹配 50ms + TTS 缓存命中 50ms + 渲染 300ms |
| 向量命中（L3） | ≤ 1.5s | 上述 + 检索 100ms + 可能的实时 TTS 400ms |
| LLM 兜底（L4） | 文字首屏 ≤ 3s，发音 ≤ 8s | ASR 出文本即回显；LLM 流式先出中英文，音标与 TTS 后补 |

三条强制约束。LLM 路径一律异步，任何情况下不得让母亲对着空白屏等待。界面必须在 800ms 内出现可见变化（把识别到的中文回显出来），这一项对体感的影响大于总时长。TTS 不可用时返回文字结果并提示「发音暂时不可用」，不阻断整个流程。

### 4.2 学习模式（M2）

三个模式共享同一套词条库与返回结构，差异在「呈现顺序与交互重心」。

| 模式 | 入口 | 交互重心 | 适用时段 |
|---|---|---|---|
| 情景短句 | 首页「短句」 | 按生活时段浏览短句卡，逐句听 + 跟读 | 起床 / 吃饭 / 睡前等固定时段 |
| 单词学习 | 首页「学单词」 | 按场景分类，逐词呈现，看图—听音—跟读 | 固定学习时段 |
| 单词复习 | 首页「复习」 | 按复习排期推送已学词，听音选图 / 跟读 | 每日复习时段 |

**M1 与 M2 的边界**：M1 语音问答是无编排的自由提问，随时发起、即问即答，它本身不属于 M2 的任何一个模式（v0.3 把它同时叫作「日常对话模式」造成了页面职责重叠，此版更正）。M2 的三个模式都是有编排的学习流，共同点是内容由应用决定顺序，而不是由母亲临时想到什么问什么。

**单词学习模式单词流**：展示图 → 播标准音 → 母亲跟读 → 幼儿跟读录音 → 进入下一个。每 5 词一组。B 段（24 月+）组末弹出复习小测（听音点图）；A 段跳过小测，直接进入组末鼓励，因为 24 月以下幼儿无法稳定完成选择题，强行加测只会制造挫败。

**单词复习模式**：仅推送昨日及之前学过且掌握度低的词，掌握度算法见 8.6。复习形式以「听音选图」（仅 B 段）与「跟读录音」为主，不引入拼写。需要说明的是，标准间隔重复算法依赖「回忆是否正确」这一可测信号，而 1~3 岁幼儿无法自评、也不能可靠地被测验，因此本产品的复习排期实质是「固定间隔轮播 + 母亲主观标记修正」，不宜对外宣称为艾宾浩斯算法，避免用一个精确的名字掩盖一个粗糙的机制。

### 4.3 发音录制与对比（M3）

**功能描述**：在单词卡或句子卡上提供明显录音按钮，录下幼儿跟读，随后可同时回放标准音与幼儿录音做对比。**不做严格打分**，因为 1~3 岁发音不准是常态，打分会打击积极性。

**交互设计**：

| 步骤 | 元素 | 反馈 |
|---|---|---|
| 1 准备 | 大圆形录音按钮，中央麦克风图标，按钮下方文字「点一下开始」 | 点下按钮变色放大 |
| 2 录音 | 点按开始后持续录音，按钮显示波形动画与计时；静音 1.5s 由 VAD 自动结束，也可再点一次手动结束 | 结束时轻提示音 |
| 3 回放 | 先播标准音再播幼儿录音各一遍，并排两个播放条 | 提供重录按钮 |
| 4 鼓励 | 弹出随机表扬（Great job! / Well done!）配表情动效 | 无论发音如何都鼓励 |

**为什么不用「按住说话」**：母亲侧的 ASR 输入用按住式没问题（见 6.1），但幼儿侧不行。持续按压是一项要到 2.5 岁前后才稳定的精细动作，A 段幼儿按住即松、松了又按，会大量产生 0.3 秒的废录音。改为「点一下开始、静音自动停」后，A 段由母亲点按、孩子只管说，B 段幼儿也能自己完成。这是 v0.3 到 v0.4 之间最实质的一处交互修正。

**关于相似度打分**：v0.3 保留了一个「基于音素对齐给出 0~100 参考值」的可选功能，此版**在 MVP 与 V1 均不做**，理由有两条。技术上，强制对齐依赖声学模型对目标音素的稳定预测，而幼儿含糊、气声多、时长不定的发音会让对齐结果接近噪声，给出的数字不比随机数更有信息量；产品上，一个不可靠的数字一旦显示出来，母亲一定会当真，这与 4.3 开头「不做严格打分」的原则直接冲突。

替代方案是把判断权还给在场的母亲：回放后提供「学会了 / 再练练」两个一键标记。母亲的耳朵和对孩子的了解，在这个场景里比任何算法都准，而且这个标记正好是 8.6 掌握度的主信号。`recording.similarity` 字段保留为可空，供后续真的验证出可用方案时再启用。

**录音存储**：见 8.4。默认保留最近 30 天，母亲可手动收藏长期保留。

### 4.4 TTS 语音合成（M4）

**功能描述**：为词条与句子合成英语发音。采用本地部署的轻量神经 TTS。

**方案选型建议**（详见 9.4）：

| 方案 | 音质 | 资源占用 | 推荐度 |
|---|---|---|---|
| Piper（ONNX） | 好 | CPU 可跑，约 200MB 模型 | 首选 |
| Coqui TTS | 较好 | 需 GPU 才流畅 | 备选 |
| espeak-ng | 一般 | 极轻 | 兜底，音质差不推荐做启蒙 |

**关键约束**：发音必须清晰、语速可调（默认慢速 0.8x，便于幼儿捕捉音节），支持美式英语优先（启蒙阶段统一一种口音）。

### 5.3 核心页面流程

**语音问答流**：

```
首页 → 点「问一问」→ 语音问答页
  → 按住录音 → 上传 → ASR → 识别文本回显（≤800ms）
  → 匹配管线 L0~L4 → TTS
  → 结果卡（播一次发音）
  → 母亲可点播放重听 / 点「跟读」进入录音对比
  → 录音对比页（标准音 vs 幼儿录音）→ 母亲标记「学会了/再练练」→ 鼓励弹窗 → 返回或继续问

异常分支：
  ASR 无结果  → 「没听清，再说一次」+ 文字输入入口
  匹配临界    → 「你是说 A 还是 B？」二选一确认
  彻底未命中  → 相近词推荐 + 文字输入 + 静默写入未命中表（8.8）
  TTS 不可用  → 出文字卡 + 「发音暂时不可用」，不阻断
```

**单词学习流**：

```
首页 → 点「学单词」→ 学习模式页 → 选「单词学习」
  → 选场景（物品/人物/...）→ 单词学习页
  → 逐词：图 → 标准音 → 母亲跟读 → 幼儿录音
  → 每 5 词：B 段走小测，A 段直接给组末鼓励
  → 返回首页
```

**单词复习流**：

```
首页 → 点「复习」→ 单词复习页（自动推送待复习词）
  → 听音选图（仅 B 段） → 跟读录音 → 母亲标记 → 掌握度更新
  → 全部完成 → 复习总结 → 返回首页
```

### 5.4 异常状态与降级

产品层面必须定义的异常状态，缺一个就会在真实使用里变成一次「应用坏了」的印象。母亲带着孩子在场时的容错窗口极短，任何一次白屏都可能是最后一次打开。

| 状态 | 触发 | 界面表现 | 可恢复动作 |
|---|---|---|---|
| 麦克风权限被拒 | 首次或系统设置关闭 | 顶部常驻提示条 + 图文引导去系统设置开启 | 直接切文字输入模式继续用 |
| 非 HTTPS 访问 | 用 IP 或 http 打开 | 明确提示「当前地址无法录音」，给出正确地址 | 跳转 HTTPS 地址 |
| 网络中断 | 弱网或服务器不可达 | 已缓存词条离线可查可播，未缓存的提示稍后重试 | 恢复后自动重试队列 |
| 推理服务未就绪 | 容器启动中 | 首页顶部「正在启动，约 1 分钟」 | 就绪后自动解除 |
| 录音过短 | 时长 < 0.5s | 不入库，提示「这次没录到，再来一次」 | 一键重录 |
| 磁盘将满 | 音频目录超阈值 | 设置页告警 + 提示清理过期录音 | 一键清理 30 天前非收藏录音 |
| 屏幕时间用尽 | 达到每日上限 | 柔性收尾页（今日小结 + 吉祥物道别），不硬弹窗 | 母亲可查看日报，不可继续学习 |

## 6. 交互设计规范

### 6.1 语音输入交互

母亲侧语音输入采用「按住说话」式（press-to-talk），不采用 always-on 监听，避免误触发与隐私顾虑。这里用按住式是合理的——母亲是有完整精细动作能力的成年人，与幼儿侧的录音按钮（见 6.2）不能套用同一套交互。按钮直径不小于 64px，按下时按钮放大并显示实时音量波形，松开后显示「识别中…」状态，时延按 4.1.3 的分路径预算执行，识别文本要在 800ms 内回显。识别失败时提供「再说一次」与「改用打字」两个兜底，连续两次失败则主动把文字输入框展开，不让母亲自己去找。

### 6.2 录音按钮设计

幼儿侧录音按钮是整个产品最关键的单一控件，设计要求：

| 维度 | 要求 |
|---|---|
| 尺寸 | 直径 ≥ 88px（幼儿手指精细动作有限） |
| 位置 | 屏幕中下方，拇指与幼儿伸手可达 |
| 颜色 | 高饱和（建议暖橙 #FF8A3D），按下变深并放大 1.1 倍 |
| 图标 | 中央麦克风图形，下方文字「点一下，跟我读」 |
| 交互 | 点按开始录音 + 波形动画 + 计时；静音 1.5s 自动结束，或再点一次手动结束 |
| 容错 | 时长 < 0.5s 不入库，提示「这次没录到，再来一次」；超时 15s 自动截断（幼儿跟读一个词或一句话不会更长） |
| 分段差异 | A 段由母亲点按，按钮可放在母亲惯用手侧；B 段幼儿自行点按，按钮居中 |

需要强调的是「点按 + VAD 自动停」而不是「按住说话」，理由见 4.3。这一处如果照抄成人语音应用的按住式交互，A 段幼儿会产出大量废录音，母亲很快就会放弃这个功能。

### 6.3 反馈机制

三层反馈：操作层（按钮按压动效）、内容层（结果卡出现 + 自动播放）、激励层（录音后表扬贴纸）。1~3 岁对正反馈高度敏感，每次跟读后无论发音如何都给鼓励，且鼓励文案随机（Well done / Great job / Good try / You did it），避免机械重复。

### 6.4 幼儿友好的视觉与触觉设计

| 维度 | 规范 |
|---|---|
| 字号 | 中文 ≥ 24px，英文 ≥ 32px，音标 ≥ 20px |
| 配色 | 高饱和、高对比；浅色背景 + 深色文字；正文对比度不低于 4.5:1，大字号不低于 3:1；不用颜色作为唯一信息载体 |
| 图标 | 全部配实物照片或高识别度插画，不用抽象线性图标 |
| 动效 | 转场 200~300ms，按钮按压 100ms，避免闪烁 |
| 音效 | 操作有轻柔提示音，错误音避免刺耳 |
| 单屏信息 | 单屏不超过一个核心任务，避免分屏信息过载 |

### 6.5 母亲侧操作流

母亲侧的关键操作（切换模式、调整语速、查看日报、导出数据）放在屏幕右上角与「我的」「设置」两个 Tab，与幼儿主操作区物理分离，避免幼儿误触改变设置。所有设置项默认值对新手最友好（语速 0.8x、单次会话 5 分钟、屏幕时间上限按年龄分段见 11.3）。

### 6.6 纯音频模式（A 段默认）

这是本版新增的一个模式，用来正面回应「1~2 岁本不该有屏幕时间」这个绕不开的矛盾（见 11.3）。

纯音频模式下，应用不给幼儿看画面：手机可以扣在桌上或放在母亲手里，屏幕只对母亲呈现极简的词卡（英文 + 音标 + 播放键），幼儿侧的全部输入都是声音。母亲听一遍、跟读一遍、教给孩子，孩子跟读，应用录音。整个闭环里孩子一次屏幕都不用看。

| 项 | 规则 |
|---|---|
| 默认开关 | A 段（12~24 月）默认开启，B 段默认关闭，母亲可随时切换 |
| 界面 | 母亲侧极简单页，大播放键 + 大录音键，无动画、无贴纸、无图片 |
| 屏幕时间计量 | 纯音频模式下的时长**不计入幼儿屏幕时间**，只计入亲子学习时长 |
| 技术要求 | 锁屏后音频可继续播放与控制（Media Session API）；iOS PWA 的后台音频行为需实测，若不可用则退化为亮屏但息内容的「黑屏播放页」 |

这个模式还有一个副作用上的好处：它天然逼着产品把「发音准不准」做扎实，因为没有画面可以掩饰。

### 6.7 首次启动引导（Onboarding）

首次打开的三分钟决定这个应用会不会有第二次打开。引导只做三步，不做长教程，目标是让母亲在离开引导之前就完整成功地跑通一次问答。

第一步问孩子的出生年月，用来自动确定 A/B 分段与初始难度，顺带说明「为什么问」——一句「我们会按月龄调整跟读方式」就够，不做冗长解释。第二步申请麦克风权限，申请前先用一句话讲清用途（「用来听你说中文，以及录下宝宝的跟读」），被拒绝时不反复弹窗，直接切到文字输入并在设置里留开启入口。第三步是一次带手把手提示的示范问答，固定用 cup 这类必然命中且发音清晰的词，走完「问 → 出卡 → 播发音 → 跟读录音 → 回放」全流程。

引导全程不超过 6 个操作步骤，任何一步都可跳过。如果母亲跳过了生日填写，默认按 B 段处理并在设置页顶部保留一条待补提示。

## 7. 亲子互动增强功能

在核心需求之上，增加以下功能以提升亲子互动质量与持续使用动机。这些功能不是「产品噱头」，而是直接服务「母亲坚持教、幼儿愿意学」的核心矛盾。

### 7.1 学习成就与奖励（M6）

| 元素 | 触发 | 呈现 |
|---|---|---|
| 星星 | 每完成一个词学习或一次录音 | 顶部星星计数 +1 |
| 勋章 | 累计学满一个场景 / 连续打卡 7 天 | 我的页勋章墙 |
| 每日打卡 | 当日完成至少 1 次录音 | 首页打卡日历，连续天数可视化 |
| 打卡保护（Streak Freeze） | 每月自动赠送 2 次 | 断签当天不计中断，保留连续天数 |

打卡保护借鉴 Duolingo 的 Streak Freeze：带娃家庭难免因生病、外出等中断，一次断签不应清零，否则母亲容易因「断了就没意义」彻底放弃。每月默认赠送 2 次，用完需重新累计。奖励仅用于自我激励，不与任何消费或外部兑换挂钩。

### 7.2 亲子任务卡（M7）

每日推送一张「今日亲子任务」卡片，把英语启蒙嵌入生活场景。例如「今天吃饭时，和宝宝一起说三次 yum yum」「出门前说 let's go」。任务卡附教学要点（母亲侧可展开），完成勾选后计入日报。任务卡由应用内置模板生成，母亲也可自定义。

### 7.3 学习日报（M8）

每日 21:00 生成当日学习日报，内容含：学习词数、新学词列表、当日录音回放、连续打卡天数、明日推荐复习词。母亲可在「我的」查看历史日报。日报定位为「轻量复盘工具」，不堆数据，一屏可读完。

### 7.4 表扬音效与贴纸（M10）

录音完成后随机弹出一张表扬贴纸（动物角色举大拇指、星星烟花等）配短句鼓励音效。贴纸可收藏到「我的贴纸本」，幼儿可翻看。

与 MVP 的边界：4.3 第 4 步的鼓励在 MVP 就有，但那只是随机文案配一个表情动效，成本极低；M10 指的是可收藏、可翻阅、有集齐感的贴纸本，需要美术资源与收藏体系，属于 V2。两者不要在排期上混为一谈。

### 7.5 母亲学习卡（M9，重要增强）

针对「母亲英语水平有限」这一核心约束，单设母亲学习卡：每次幼儿学一个词，母亲侧同步收到一张小卡，含该词的发音要点（如 th 咬舌尖）、易错点、生活用法例句。母亲侧学习卡每日汇总，可在「我的」复习。这是「边学边教」闭环的关键补全——母亲自己也得学。

|---|---|---|

| learn_count | int | 学习次数 |
| review_count | int | 复习次数 |
| last_mother_marks | json | 最近 3 次母亲标记，如 `["got_it","keep_trying","got_it"]` |
| last_quiz_results | json | 最近 3 次小测结果（仅 B 段产生） |
| last_touched_at | datetime | 最近一次学习或复习时间 |
| next_review_at | datetime | 下次推送时间 |
| mastery | float | 0~1 综合掌握度，算法见下 |

**掌握度算法（v0.4 修订）**：v0.3 的公式里 `avg_similarity` 占 0.5 权重，而 4.3 已论证该信号在幼儿场景下不可靠且 MVP/V1 不产出——一个核心排序算法的一半权重建立在一个不存在的字段上，必须重写。新算法以母亲标记为主信号：

```
signal_m = 最近 3 次母亲标记均值（got_it = 1，keep_trying = 0），无标记则为空
quiz_acc = 最近 3 次小测正确率，无则为空
exposure = min(learn_count + review_count, 6) / 6
recency  = 1 - min(距 last_touched_at 天数, 14) / 14

有母亲标记：        mastery = 0.55 * signal_m + 0.25 * exposure + 0.20 * recency
无标记但有小测：    mastery = 0.45 * quiz_acc + 0.35 * exposure + 0.20 * recency
两者皆无：          mastery = 0.65 * exposure + 0.35 * recency
```

**复习排期**：不使用间隔重复算法的标准实现，改为按掌握度分档的固定间隔，理由见 4.2。掌握度低于 0.3 次日再推，0.3~0.6 隔 3 天，0.6~0.85 隔 7 天，0.85 以上隔 21 天且此后不再主动推送，只在母亲手动翻阅时出现。掌握度全程只用于决定推送顺序，不向幼儿侧暴露任何数值或等级。

### 8.8 未命中查询 UnmatchedQuery

匹配管线彻底未命中时落表，是词库扩充的唯一可靠输入源（见 3.7、4.1.1）。这张表不该被当成日志，它是产品资产。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | string | 主键 |
| family_id | string | 外键 |

| llm_result | json | 若走到 L4，记录 LLM 生成结果，供人工审核后入库 |

### 8.9 索引与约束要点

匹配管线的性能预算（4.1.3 要求 L1 在 5ms 内）依赖索引，这里一并写明，避免实现时遗漏。

`word.zh` 与 `word.aliases` 需要可检索：SQLite 下用一张 `word_alias(alias, word_id)` 展开表加唯一索引，比在 JSON 字段里扫描快一个数量级，别名的写入与词条保存放在同一事务。`progress` 用 `(child_id, target_type, target_id)` 复合主键，另建 `(child_id, next_review_at)` 索引支撑复习推送查询。`recording` 建 `(child_id, created_at)` 与 `expires_at` 索引，后者供过期清理任务扫描。`unmatched_query` 对 `normalized_text` 建唯一索引，重复出现走 `hit_count + 1` 而不是插新行。所有 datetime 统一存 UTC，跨天聚合时再转本地时区（见 9.10）。

## 9. 技术架构建议

### 9.1 整体架构

采用「Rust 业务后端 + 推理服务分离 + Docker 编排」架构。Rust 后端承担 API、业务逻辑、数据库、用户与模型配置、学习进度编排；AI 推理（TTS/ASR/LLM）作为独立服务，Rust 通过 HTTP 或 FFI 调用，便于独立扩缩容与热替换。

```
[移动端 PWA] ──HTTPS── [Nginx 反代]
                            │
                ┌───────────┴───────────┐
                │                       │
        [Rust 业务后端]          [静态资源]
        (axum/actix-web)         (PWA 前端)
                │
        ┌───────┼───────────┬───────────┐
        │       │           │           │
    [SQLite]  [TTS推理]   [ASR推理]   [LLM推理]
    (数据)  Piper(ONNX)  sherpa-onnx  llama.cpp/ollama
            Rust ort crate   FFI/HTTP    HTTP(OpenAI兼容)
```

全部服务用 docker-compose 编排，单机部署。前端 PWA 可装手机桌面，离线缓存静态资源，音频走流式接口。推理服务统一用 Python 实现（AI 生态最齐：vLLM、transformers、Coqui TTS、sherpa-onnx Python 绑定都现成），Rust 后端通过 HTTP 调用，业务与推理解耦，各取所长。

### 9.2 前端方案

| 维度 | 选择 | 理由 |
|---|---|---|
| 形态 | PWA（H5 + Service Worker） | 个人服务器部署，免审核，跨平台，可装桌面图标 |
| 框架 | Vue 3 + Vite 或 React + Vite | 轻量，生态成熟 |
| 音频 | MediaRecorder API | 浏览器原生录音 |
| 离线 | Service Worker 缓存静态资源 | 弱网可用 |
| 不选 | 原生 App / 小程序 | 个人项目无需审核与分发，PWA 成本最低 |

录音权限需 HTTPS，个人服务器需配证书（Let's Encrypt 免费证书或自签 + 本地信任）。用 IP 或 http 直接访问时浏览器会禁用麦克风，这一条要在部署文档和应用内错误提示里都写清楚（见 5.4）。

**iOS 上的 PWA 限制（选 PWA 就必须接受的成本）**：v0.3 没有评估这一项，但它直接影响核心链路，实现前需在真机上逐条实测。

| 限制 | 影响 | 应对 |
|---|---|---|
| 音频播放需用户手势触发 | 「结果卡自动播一次发音」在首次会话会被静默拦截 | 在录音按钮的点击回调里解锁 AudioContext，此后本次会话可自动播放 |
| Safari 的 MediaRecorder 输出 mp4/aac，不产出 webm/opus | 9.10 里「webm/opus 转码」的假设只对 Android/桌面成立 | 后端按实际 MIME 分支处理，两种容器都要能转 16k 单声道 wav |
| 添加到主屏幕后的后台音频行为不稳定 | 影响 6.6 纯音频模式的锁屏播放 | 先实测，不可用则退化为「黑屏播放页」而非真正后台 |
| 站点存储可能被回收 | 离线缓存与未上传录音可能丢失 | 录音落盘即上传，不在前端长期堆积；缓存丢失后可静默重建 |

如果实测下来 iOS 关键能力不可用，退路是给 iOS 单独套一层 Capacitor 壳走本地安装，而不是推翻整个 PWA 方案；这属于 V2 才需要考虑的事，MVP 阶段先把安卓路径跑通。

### 9.3 后端方案

| 维度 | 选择 | 理由 |
|---|---|---|
| 语言 | Rust（axum 或 actix-web） | 性能高、内存安全、单二进制便于 Docker、并发好；个人服务器资源占用低 |
| AI 集成 | 推理服务分离，Rust 调 HTTP/FFI | 规避 Rust AI 生态弱项，业务与推理解耦（详见 9.4~9.6、9.9） |
| API 风格 | REST + 流式（音频上传 / SSE 返回进度） | 简单够用，长任务用 SSE 推进度 |
| 数据库 | SQLite（默认）/ PostgreSQL（多用户扩展） | 单机够用零运维；多家庭上量后升 Postgres |
| ORM | sqlx（编译期校验 SQL） | Rust 生态首选，类型安全，兼容 SQLite/PG |
| 部署 | Docker Compose | 一键编排，详见 9.9 |
| 音频存储 | 本地文件系统 + 静态目录 | 不引入对象存储 |
| 日志 | tracing crate | 结构化日志，便于排障 |

Rust 不直接跑大模型推理（生态不成熟），而是委托给独立服务，推理服务统一用 Python 实现：TTS 用 Piper 或 Coqui（Python）；ASR 用 sherpa-onnx（Python 绑定）；LLM 用 vLLM 或 llama-cpp-python（暴露 OpenAI 兼容 HTTP）。Rust 专注业务与编排，通过 HTTP 调推理服务，可独立替换升级。轻量 TTS（Piper ONNX）也可由 Rust 的 ort crate 直接加载省一个服务，二选一。

### 9.4 TTS 方案选型

**首选 Piper**：基于 ONNX 的神经 TTS，CPU 可跑，英语音质在轻量方案里最好，模型约 100~200MB，支持多音色。语速可调。社区有大量预训练英语音色（如 `en_US-lessig-medium`）。

**备选 Coqui TTS**：质量更高但需 GPU 才流畅，模型更大，适合有 GPU 的服务器。

**不推荐 espeak-ng**：音质机械，启蒙阶段不可接受，仅作兜底。

合成策略：高频词条与句子的 TTS 音频预生成并缓存到文件，避免每次实时合成；LLM 生成的新词再实时合成。Rust 后端用 ort crate 直接加载 Piper ONNX 模型合成，或调独立 TTS 服务；按 `model+voice+text` hash 缓存音频文件，重复词直接返回。

### 9.5 ASR 方案选型

母亲用中文提问，需中文 ASR。

| 方案 | 优势 | 劣势 |
|---|---|---|
| sherpa-onnx + 中文模型 | 流式、轻量、CPU 可跑、中文识别好 | 模型稍大 |
| whisper.cpp（small/base） | 多语言、精度高 | 非流式，延迟略高 |
| 云端 ASR | 最准 | 不符合本地化目标，不选 |

**首选 sherpa-onnx** 流式中文模型，兼顾本地化与低延迟。若服务器算力充裕，可用 whisper.cpp base 模型做非流式，精度更高。Rust 后端通过 sherpa-onnx 的 C++ 核心 FFI 绑定调用，或起独立 ASR 服务走 HTTP。注意浏览器录的 webm/opus 需用 ffmpeg 转 16kHz 单声道 wav 再送 ASR。

### 9.6 LLM 选型

LLM 用于：词条库未命中时的语义归一与生成、母亲学习卡内容生成、句子场景化扩展。

| 方案 | 优势 | 劣势 |
|---|---|---|
| 本地小模型（Qwen2.5-7B-Instruct 量化） | 全本地、无 API 费用 | 需约 6GB 显存或大内存 |
| 本地更小（Qwen2.5-3B） | 资源更低 | 生成质量略降 |
| 云端 API（如通义/OpenAI 兼容） | 质量稳、零部署 | 有费用、数据外发 |

**建议**：优先走词库匹配管线（见 4.1.1），未命中才走 LLM。这里必须纠正 v0.3 的一处表述——「词条库覆盖 90% 高频场景」是一个**未经验证的假设**，且同一文档 9.7 处又写成 95%，两个数字都没有依据。真实覆盖率取决于母亲的提问分布，只能靠 MVP 上线后的未命中率（见 13.2）实测得出，在此之前不应把它当作已知条件来做架构决策。

LLM 的部署选择按有无 GPU 分岔，且这个分岔比 v0.3 描述的更硬。无 GPU 时不建议跑本地 LLM：CPU 上 7B 量化模型的生成速度大约每秒个位数 token（量级估算，需实测），生成一份含中英文、例句、母亲提示的结构化 JSON 需要一二百 token，实际等待会到几十秒，与 4.1.3 的任何一档预算都不在同一量级；3B 快一些但仍是十秒级，且生成质量对启蒙内容而言已经勉强。因此无 GPU 的默认路径是「词库 + 用户自配云端 API」，本地 LLM 只在有 GPU 时启用。云端路径涉及数据外发，必须满足 11.4 的知情同意要求。

LLM 输出强制结构化 JSON，prompt 模板固化，音标字段一律丢弃不用（见 4.1.2），避免自由生成带来不安全或不准确的内容。

**推理服务分离**：LLM 不嵌 Rust 后端，而作为独立推理服务运行——本地优先 llama.cpp 的 server 模式或 ollama（都暴露 OpenAI 兼容 HTTP），Rust 后端按用户配置路由调用。模型可热切换、不重启后端，也方便每户用不同模型。

**推理服务技术栈**：TTS、ASR、LLM 三个推理服务均用 Python 实现，因为 Python 的 AI 推理生态最齐——LLM 用 vLLM（GPU）或 llama-cpp-python（CPU），TTS 用 Coqui TTS 或 Piper 的 Python 包，ASR 用 sherpa-onnx / faster-whisper 的 Python 绑定。每个推理服务封装成独立 FastAPI 微服务，暴露 HTTP，Rust 后端统一调用。这样 Rust 管业务性能与并发，Python 管推理生态与迭代速度，各取所长。轻量的 Piper ONNX 也可让 Rust 用 ort crate 直接加载以省一个容器，作为可选优化。

**用户级模型配置**：支持每个家庭/用户配置自己的 LLM、TTS、ASR 模型（见 9.8），即用户可填自己的 OpenAI 兼容 API Key、或选本地模型、或配语音模型与本地 TTS。后端按用户配置路由到对应推理服务，密钥加密存储（见 9.10）。

### 9.7 本地化部署硬件参考

Rust 后端本身资源占用极低（常驻几十 MB），瓶颈在推理服务，硬件需求主要由 TTS/ASR/LLM 决定，与后端语言无关。

| 配置 | 适用 | LLM 策略 |
|---|---|---|
| 2 核 CPU / 4GB 内存 / 无 GPU | MVP 起步：Rust 后端 + Piper + sherpa-onnx | 不跑本地 LLM，未命中走兜底提示 |
| 4 核 CPU / 8GB 内存 / 无 GPU | V1 常见家用小主机 | 不跑本地 LLM，未命中走用户自配云端 API |
| 8 核 CPU / 16GB 内存 / 无 GPU | 同上，余量更足 | 本地 3B 仅可用于离线批量补词等非实时任务 |
| 含 GPU 6GB+ 显存 | V1+ | 本地 Qwen 7B 量化可承担实时兜底 |

结论是无 GPU 时不要试图把本地 LLM 塞进实时问答链路。这不是性能调优能解决的问题，量级差得太远。无 GPU 场景下应该做的是把词库和别名表做厚（这是 3.7 内容生产的价值所在），让 L1/L2 尽量兜住，实在兜不住时走云端或落未命中表，而不是让母亲对着转圈等半分钟。

### 9.8 数据库设计

在 8.x 已有词条、学习记录、录音、进度、成就表基础上，补充用户与模型配置相关表。默认 SQLite，多家庭上量后可平滑迁 PostgreSQL（sqlx 抽象层兼容两者）。

| 表 | 关键字段 | 说明 |
|---|---|---|
| family 家庭 | family_id, mother_name, created_at | 一个家庭账号 |
| child 孩子 | child_id, family_id, name, birthdate, level | 一家庭可多孩 |
| user_account 账号 | user_id, family_id, role(mother/admin), password_hash | 登录账号 |
| model_config 模型配置 | config_id, family_id, type(llm/tts/asr), provider(local/openai/ollama), model_name, endpoint, api_key_enc, params | 每户配自己的模型集；密钥加密存（见 9.10） |
| family_model_binding 绑定 | family_id, llm_config_id, tts_config_id, asr_config_id | 家庭当前启用哪套模型 |
| progress 学习进度 | 见 8.6 | 掌握度、下次复习时间 |
| learning_record 学习记录 | 见 8.3 | 每次 learn/review/quiz/ask |
| recording 录音 | 见 8.4 | 幼儿录音，30 天过期 |
| word_alias 别名展开 | alias, word_id | 支撑 L1 精确匹配的检索表，见 8.9 |
| unmatched_query 未命中 | 见 8.8 | 词库扩充的输入源 |

模型配置要点：type 区分 LLM / TTS / ASR；provider 支持 local（指向本地推理服务地址）、openai 兼容（用户填 key 调云端）、ollama（本地 ollama 服务）；语音模型与本地 TTS 也走这张表，Piper 等本地 TTS 用 provider=local + model_name=piper-xxx。后端收到请求时按 family_model_binding 路由到对应推理服务。

### 9.9 Docker 部署

最终交付 docker-compose 编排，一键部署。服务拆分如下：

| 服务 | 镜像/构建 | 作用 |
|---|---|---|
| backend | Rust 后端（多阶段构建，distroless 最终镜像） | API、业务、编排 |
| web | nginx + PWA 静态产物 | 前端 + 反代 |
| tts | Piper ONNX 服务（或 Rust 后端内嵌 ort） | 英语 TTS |
| asr | sherpa-onnx / whisper.cpp 服务 | 中文 ASR |
| llm | Python 推理服务（vLLM / llama-cpp-python）或 ollama | LLM 推理（可选，无 GPU 可不启） |
| db | SQLite 文件挂载卷 / 或 postgres 容器 | 数据 |

关键点：推理服务设 healthcheck 与 depends_on（LLM 启动慢，后端等就绪）；模型文件用 named volume 挂载避免重复下载；音频文件用 volume 持久化；.env 管理 secret 与各服务地址；用 profiles 区分 mvp（不启 llm）/ full（全启）。示例结构：

```
services:
  web:        # nginx + 前端
  backend:    # rust api, depends_on tts/asr
  tts:        # piper, healthcheck
  asr:        # sherpa-onnx, healthcheck
  llm:        # ollama, profiles: [full]
  # db 用 sqlite 文件卷，无需独立容器
volumes:
  models:     # 模型文件
  audio:      # 录音与合成音频
  data:       # sqlite 文件
```

### 9.10 其他技术实现建议

- **密钥加密**：用户 API Key 用服务器主密钥（env 注入）做 envelope 加密存库，不明文、不进日志、不进 commit。
- **音频转码**：浏览器录音格式按平台分支——Android/桌面 Chrome 产出 webm/opus，iOS Safari 产出 mp4/aac，两者都用 ffmpeg 转 16kHz 单声道 wav 再送 ASR，不要写死单一容器；合成音频压 Opus 减带宽。
- **云端模型的数据边界**：启用云端 LLM 时，只发送 L0 归一后的中文文本，不发原始音频、不发孩子姓名与生日、不发学习记录。请求前在设置页做一次显式告知与确认，确认状态入库可撤销（呼应 11.4）。
- **TTS 缓存**：按 `model+voice+text` hash 缓存合成音频，重复词直接返回文件。
- **配置热更新**：模型配置改库后即时生效，不重启后端（每次请求读绑定或短缓存）。
- **时区**：学习进度按本地日期聚合（打卡、日报），存储用 UTC，查询转本地时区，避免跨天错算。
- **就绪与熔断**：推理服务不可用时后端降级（TTS 挂返回文字 + 提示、LLM 挂回落词条库），不整页报错。
- **备份**：SQLite 文件 + 录音目录 + 模型配置，定时脚本打包到独立目录，支持一键导出（呼应 11.4 隐私要求）。
- **可观测**：tracing 结构化日志 + /healthz、/readyz 端点，便于容器编排探活。

## 11. 风险与约束

### 11.1 技术风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 无 GPU 时 LLM 响应慢 | 问答从 2 秒退化到几十秒，量级不可接受 | 无 GPU 直接不启本地 LLM（见 9.7）；词库与别名做厚；云端兜底需用户同意 |
| 词库实际命中率远低于预期 | 母亲频繁碰壁，几次之后弃用 | 分层匹配管线（4.1.1）；未命中表驱动补词；MVP 阶段把未命中率当作头号观测指标 |
| TTS 音质不足 | 发音不准误导幼儿 | 用 Piper 而非 espeak；每个词条音频人工试听校验 |
| LLM 生成音标错误 | 母亲照着念错，孩子记错 | 音标只取词典与 g2p，丢弃 LLM 输出（见 4.1.2） |
| ASR 在嘈杂环境识别差 | 母亲体验受挫 | 提供文字输入兜底；录音键加降噪提示；置信度低时给二选一确认 |
| iOS PWA 关键能力受限 | 自动播放、后台音频、录音格式与预期不符 | 实现前真机实测四项（见 9.2）；不可用则降级而非改架构 |
| 内容生产工作量被低估 | 代码写完了但没有可用内容，项目卡在最后一米 | 内容与代码并行推进；MVP 内容量压到 58 条；LLM 出初稿人工校验（见 3.7） |
| 个人服务器带宽小 | 音频传输慢 | 静态资源本地缓存；音频压缩 Opus；高频音频前端预缓存 |

### 11.2 内容风险

LLM 自由生成可能输出不当内容或错误内容。缓解手段分三层：LLM 输出强制结构化 JSON 并做白名单校验（词性、长度、字符集），音标字段直接丢弃不用（见 4.1.2，格式校验拦不住「格式合法但音节错」这种最危险的情况）；母亲学习卡与幼儿呈现内容用分开的 prompt，前者可以出现语言学解释，后者只出现可直接照说的内容；上线前对词条库人工校音，LLM 实时生成的结果先进「待入库候选」，人工确认后才进正式词库。

### 11.3 使用风险（幼儿屏幕时间）

这是本产品最需要正面回答、也最容易被自己糊弄过去的一条：**主流育儿指南对 24 月龄以下幼儿的建议是不安排屏幕时间**（WHO 2019《5 岁以下儿童身体活动、久坐行为和睡眠指南》对 1 岁不建议久坐屏幕时间，对 2 岁建议不超过 1 小时且越少越好；AAP 对 18~24 月建议仅在家长陪同下接触高质量内容。以上为通常理解，产品内正式引用前需核对指南最新版本原文）。而本产品的目标用户下限是 12 月龄，如果不做区分地给出「每日 15 分钟」，就是在替家长突破一条本不该突破的线。

解法是 6.6 的纯音频模式：A 段（12~24 月）默认不给孩子看屏幕，孩子只听声音，母亲看屏幕。这样产品对 A 段的幼儿屏幕时间是零，且不影响核心教学闭环。

| 分段 | 幼儿屏幕时间 | 单次会话 | 睡前 |
|---|---|---|---|
| A 段 12~24 月 | 默认 0（纯音频模式），母亲若手动关闭该模式则上限 5 分钟/天 | 3 分钟 | 21:00 后柔性劝退 |
| B 段 24~36 月 | 默认上限 15 分钟/天，可下调不可上调 | 5 分钟 | 21:00 后柔性劝退 |

到点的处理方式是柔性收尾而非硬切断：走一个小结页，吉祥物道别，母亲仍可查看日报。硬弹窗中断会让孩子哭闹，最终被怪罪的是应用，母亲下次就不开了。文档与产品内显著位置都要写明：本产品替代不了真人互动，母亲全程参与是它成立的必要条件，不是推荐做法。

### 11.4 隐私与数据安全

录音与学习记录属未成年人敏感数据。全部本地存储，不出服务器；默认不开启任何上传或云同步；如需远程访问走家庭内网或加密通道；录音默认 30 天过期自动清理。设置页提供一键导出与一键清空。

**需要指出 v0.3 的一处自相矛盾**：本节承诺「全部本地、不出服务器」，而 9.6 与 9.8 又允许母亲配置云端 LLM/ASR 的 API Key。一旦启用云端模型，母亲的提问文本（很可能包含孩子的小名、家庭称谓、生活细节）就会离开服务器，两条声明不能同时为真。此版按以下方式收敛：

默认全本地是产品承诺，云端是母亲可主动打开的例外。开启云端模型时，设置页必须做一次明确告知（说清会发送什么、发给谁）并要求二次确认，确认状态入库且可随时撤销。云端请求只发送 L0 归一后的中文文本，不发原始音频、不发孩子姓名与生日、不发学习记录与录音（技术约束见 9.10）。产品对外的隐私说明措辞相应改为「默认全本地存储；云端模型为可选项，开启后仅外发提问文本」，不再笼统宣称「数据不出服务器」。

### 11.5 内容素材与版权

个人自用不等于没有版权边界，尤其 M13 儿歌模块存在一个容易踩空的地方：Twinkle Twinkle、Old MacDonald 这类经典儿歌的**曲调与歌词属公有领域，但网上现成的演唱录音基本都有独立版权**，直接下载音频文件放进应用属于使用他人录音制品。可行做法是用 TTS 或自行演唱生成音频，或选用明确标注 CC0 / 公有领域录音的来源，并在 `word.image_source` 同类字段上为音频也留一个来源标记。

配图同理。优先用自家实物照片（见 3.7），既没有版权问题又对幼儿更有效；确需图库时只取 CC0 或等价许可，并逐条记录来源，不用「反正个人用」来跳过这一步——一旦后续有任何对外分享的念头，没有来源记录的素材就是无法清理的债。

### 12.3 主动舍弃点及理由

借鉴必须取舍。以下机制在成人向应用里有效，但对 1~3 岁场景主动舍弃：

| 舍弃点 | 来源 | 舍弃理由 |
|---|---|---|
| Hearts 心系统 / 错误惩罚 | Duolingo | Duolingo 自承「最有争议的功能」；1~3 岁发音不准是常态，惩罚错误直接摧毁积极性。本产品录音后无论发音如何都鼓励 |
| Leaderboards 竞争排行榜 | Duolingo | 1~3 岁无需竞争；家庭自用无其他用户可比，引入排行榜无意义且制造焦虑 |
| XP 经验值数字 | Duolingo | 幼儿不懂数字含义，用星星、贴纸等具象激励更直观 |
| 付费订阅 / 内购 / 广告 | Duolingo / Babbel 等 | 个人项目，面向幼儿不应有任何商业诱导，遵守儿童应用无广告原则 |
| 复杂天赋树 Crowns | Duolingo | 树状进度对幼儿太抽象，改用线性场景关卡 + 具象勋章 |
| 母语者真人视频 | Memrise | 持续产出成本高，个人项目难维持；用 TTS + 插画 + 吉祥物替代 |

### 12.4 设计原则补充

借鉴后强化一条原则：**所有游戏化机制服务于「母亲坚持教、幼儿愿意学」这一核心矛盾，不服务于留存指标本身**。Duolingo 的 Streak 能让人「为保打卡而打卡」，对成人可接受，对幼儿场景必须避免——打卡保护、星星、贴纸都只是降低放弃成本的脚手架，不是目的。屏幕时间到点即停，不靠游戏化续命。

## 13. 成功指标与止损条件

v0.3 通篇没有定义「怎样算成功」，这是这份 PRD 最大的结构性缺口。没有判定标准的产品文档，最终会退化成一份「功能都做了」的清单，而做了不等于有用。

先说清一个前提：本产品服务单一家庭，样本量是 1，任何指标都不具备统计意义。这里定指标不是为了做数据分析，而是为了给自己一条不自欺的线——避免几个月后陷入「功能越加越多、但其实早就没人用了」的状态。

### 13.1 北极星与核心指标

北极星指标是**母亲每周主动发起教学的天数**。不是日活，不是累计学词量，也不是连续打卡天数。理由回到 1.4 的第一原则和 12.4：本产品的核心矛盾是「母亲坚持教」，母亲一旦停用，孩子那侧的一切数据都归零；反过来，只要母亲还在用，功能少一点也无妨。

| 指标 | 目标 | 说明 |
|---|---|---|
| 周教学天数 | ≥ 4 天/周 | 当天至少发起 1 次问答且完成 1 次跟读，才计为教学日 |
| 4 周留存 | 第 4 周 ≥ 3 天 | 新鲜感期过后是否还在用，这是唯一真正的检验 |
| 单次闭环完成率 | ≥ 60% | 发起问答后走完跟读录音的比例，低于此说明流程有断点 |

### 13.2 过程指标

过程指标用于定位问题出在哪一环，不作为目标本身。

| 指标 | 目标 | 对应环节 |
|---|---|---|
| 未命中率 | MVP 首月 < 20%，四周内降到 < 10% | 词库与别名覆盖（4.1.1、3.7）——这是 MVP 阶段的头号观测指标 |
| 库内问答 P95 时延 | ≤ 1.2s | 性能预算（4.1.3） |
| ASR 一次识别成功率 | ≥ 85% | 语音输入（6.1） |
| 音标与 TTS 人工校验通过率 | 100% | 内容质量红线，不达标不上线（3.7） |
| 录音废片率（< 0.5s） | < 5% | 录音交互是否合理（4.3、6.2） |

### 13.3 明确不优化的指标

以下数字可以看，但不能当目标，否则产品会朝着违背 1.4 与 12.4 的方向漂移。

幼儿屏幕时长永远只作为上限约束，不作为增长指标，越低越好而不是越高越好。连续打卡天数不进核心指标，它是降低放弃成本的脚手架，一旦被当成目标就会诱发「为保打卡而打卡」。累计学词量不作为目标，1~3 岁的语音印象建立本来就慢，追数量必然导致囫囵吞枣。会话时长同理，5 分钟到点就该结束。

### 13.4 止损条件

个人项目最缺的不是启动的动力，是停下来的判据。写在这里，到时候照着执行：

MVP 上线四周后，若母亲周均教学天数低于 2 天，**停止一切新功能开发**，先找出原因——直接问她哪一步烦，或者翻 unmatched_query 看是不是问什么都答不上来。这种情况下继续做 M2、M6、M11 只会把沉没成本堆得更高。若原因确认为词库覆盖不足，那就补内容而不是写代码；若确认为「就是没有这个使用习惯」，那就承认这个产品的假设不成立，把它缩回成一个纯查词工具，这同样是一个体面的结局。
